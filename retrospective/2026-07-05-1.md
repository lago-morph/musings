## Part 1 — what happened

### Phase 1 — plan and review gates

The user requested a major expansion of the pre-existing `tutorials/early-llm/SPEC.md`: doubled word budget, one JSON file per node with edges declared at both endpoints, a schema + CI linter, diagram prompts embedded in node JSON with style defined once, an iPad-testable UI prototype with a tap-for-prompt popup, and subagent orchestration with detailed briefs. Planning surfaced one real ambiguity ("double the budget to 40k" vs. the spec's 8–10k baseline — resolved to ~20k) and one self-inflicted mishap: after the user had already said "I take your recommendation on everything else," a follow-up question re-asked an already-answered decision ("Didn't I answer those?"). Mid-phase the user redirected: no review checkpoint after foundations, and the plan must live in the repo as a living tracker — which became `PLAN.md`, updated at every phase boundary thereafter.

### Phase 2 — foundations

Authored in-context (not delegated): `schema/node.schema.json` (draft 2020-12), `authoring/voice-and-audience.md`, `authoring/diagram-style.md` (the whiteboard style bible), `authoring/node-graph.md` with a **verbatim `edges[]` block per node** — the load-bearing trick for cross-agent consistency — plus `ci/lint_nodes.mjs` and a GitHub Actions workflow. Two findings: ajv's default export rejects draft 2020-12 schemas (fix: `ajv/dist/2020.js`), and the linter's bidirectional-edge check was self-tested with a deliberately mismatched node pair before being trusted. The calibration exemplar (`06-scaled-dot-product-attention`) exposed the value of the linter's recomputed word count: the node declared 1,380 words while containing ~854; the fix was writing the missing depth, not editing the number.

### Phase 3 — content fan-out (11 subagents)

Eleven agents (Opus for math/architecture-dense nodes, Sonnet for the rest) each received the contract files, the exemplar, verbatim edge blocks, pinned factual anchors with real citations, and the expected lint noise during partial authoring. Result: 20/20 schema-valid nodes, all 27 edges byte-identical across endpoints, 37 whiteboard SVGs — zero edge-consistency errors across the whole fan-out. Two operational findings: (a) the first push was rejected because the OAuth token lacks `workflow` scope; the GitHub MCP write fallback also failed (no contents-write), so the workflow shipped as a plain file with documented one-time activation; (b) subagent completion narration proved unreliable — several agents described their own writes as files that "already existed," one invented a "concurrent process," and integration was correctly gated on the linter and on-disk checks instead. A stop-hook nudge mid-fan-out was honored with a labeled WIP checkpoint commit (18/20) to protect work against container loss.

### Phase 4 — prototype, real-device testing, and publishing

`prototypes/build.mjs` generates the self-contained prototype (703 KB; 20 nodes + 37 SVGs inlined; hardened against `</script>` and `$`-pattern injection). Playwright testing used the globally installed Playwright's bundled Chromium (Docker daemon was started per the user's suggestion but never needed); a 21-check suite covered landing, KaTeX, diagram popup dismissal via ×/backdrop/Esc, settings toggles, and touch. Environment lessons: the sandbox's TLS-intercepting proxy broke CDN certs (`ERR_CERT_AUTHORITY_INVALID` → `ignoreHTTPSErrors`), and the ad-hoc HTTP server died with its parent shell (→ `setsid` + pre-flight curl). Real-device testing then found what automation had missed twice: the iPad **file preview doesn't execute JavaScript** (user saw a blank page → published to GitHub Pages instead), and the **Map view was unreachable above 900px** because the tab bar was hidden with no substitute — the 21-check suite had navigated via `page.evaluate(openNode(...))`, masking exactly this bug. Publishing had its own near-miss: the first `gh-pages` push tried to orphan-replace a branch that turned out to carry the repo's live Hugo docs site; the remote's non-fast-forward rejection saved it, and the prototype was added non-destructively at `/early-llm/` with deploy verification by content marker (not HTTP 200, which the stale version also returns).

### Phase 5 — the readability recovery and merge

The pivotal event. The reviewer judged the first full content pass **unreadable**: "starts right into details with no introduction… no entry point… worse than just picking up a bunch of papers," plus "diagrams are at the end of each node rather than presented in the relevant part of the text." Root cause: the voice brief encoded terseness as respect ("expert reader, no filler, earn every sentence"), and 11 agents executed it faithfully. Recovery order mattered: rewrite the **brief** (mandatory ~150-word on-ramp: where-we-are / gist / why-it-matters; inline `<figure data-dia>` anchors; "orientation is not filler"), rewrite **one exemplar**, get explicit approval ("Yes this is much better"), then re-dispatch 11 revision agents constrained to rewrite `prose` only. Completion was detected by a single background watch on a disk condition (all 20 files containing `data-dia`) rather than per-agent reactions. Provenance note: six WIP commits (`ae2c0bd`…`ab19e79`) appeared on the branch during the revision fan-out that the orchestrator did not deliberately author — one subagent attributed them to "a concurrent process"; they contained legitimate intermediate states and were kept, but unattributed commits during fan-outs are worth watching. A late stray task notification delivered full prose for three already-revised nodes from an agent never launched in this session; applying it would have reverted approved content — it was verified against a clean tree and discarded. Final state: 28,122 words, 37/37 diagrams inline, linter 0/0, PR #1 merged on the user's "Merge everything."

### Suggestion 1: Calibrate mass-produced content on one reviewer-approved exemplar before fanning out — `AGENTS-MD-10248e2e90`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-10248e2e90-calibrate-mass-produced-content-on-one-reviewer-approved-exe.md](./2026-07-05-1/AGENTS-MD-10248e2e90-calibrate-mass-produced-content-on-one-reviewer-approved-exe.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Calibrate mass-produced content on one reviewer-approved exemplar before fanning out.** "Before dispatching subagents to author or revise many content files against a shared brief, produce ONE complete exemplar, get the human reviewer's explicit approval of its voice, depth, and structure, and only then fan out. When later review feedback changes the standard, fix the brief and the exemplar first, get re-approval, then re-run the fleet — never patch the fleet's output file by file."
>
> *Grounded in: the 20-node early-LLM tutorial fan-out that had to be fully rewritten after reviewer feedback.*

**Justification** (verbatim from the per-rule file's `# justification` section):

In the early-LLM tutorial session, 11 subagents authored ~23,000 words against a brief that over-indexed on "expert reader, no filler." The reviewer's verdict on the result was "unreadable ... worse than just picking up a bunch of papers." Recovery required rewriting the authoring brief, rewriting one exemplar node, obtaining explicit reviewer approval ("Yes this is much better"), and re-dispatching 11 more subagents — roughly doubling the content-production cost of the session. The one exemplar that WAS shown to the reviewer early (scaled-dot-product-attention) is precisely where the miss was caught; had approval been gathered on it before the first fan-out, the entire second pass would have been the first. Marginal cost of the rule: one exemplar and one review round before pressing go.

### Suggestion 2: Enforce cross-file invariants with verbatim-copy blocks plus a linter, not prose instructions — `AGENTS-MD-528cd14a8b`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-528cd14a8b-enforce-cross-file-invariants-with-verbatim-copy-blocks-plus.md](./2026-07-05-1/AGENTS-MD-528cd14a8b-enforce-cross-file-invariants-with-verbatim-copy-blocks-plus.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Enforce cross-file invariants with verbatim-copy blocks plus a linter, not prose instructions.** "When N generated files must agree on shared structure (edges declared in two files, shared constants, mirrored definitions), put the canonical blocks in ONE source-of-truth file, instruct authors to copy them verbatim, and add a CI check that fails unless the copies are byte-identical. Do not rely on prose like "make sure the edges match"."
>
> *Grounded in: 27 tutorial-graph edges duplicated across 20 node files by 22 independent subagents with zero mismatches.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The early-LLM tutorial requires every graph edge to appear identically in both endpoint JSON files. Instead of asking subagents to coordinate, authoring/node-graph.md carried a ready-to-paste edges[] block per node, and ci/lint_nodes.mjs failed on any byte difference. Across two full fan-outs (22 independent agent runs, 27 edges, 20 files) the bidirectional-consistency check never once fired on a real mismatch — a class of coordination bug that prose instructions reliably produce was engineered out for the cost of one markdown file and ~30 lines of linter.

### Suggestion 7: Poll deployments for a content marker, not an HTTP 200 — `AGENTS-MD-d0a2e00e15`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-d0a2e00e15-poll-deployments-for-a-content-marker-not-an-http-200.md](./2026-07-05-1/AGENTS-MD-d0a2e00e15-poll-deployments-for-a-content-marker-not-an-http-200.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Poll deployments for a content marker, not an HTTP 200.** "When waiting for a static-site deploy (GitHub Pages or similar) to go live, poll for a unique string that only the NEW version contains (a new element id, a new phrase) rather than for HTTP 200 — the old version, a cached copy, or a soft-404 page can all return 200."
>
> *Grounded in: five GitHub Pages republish cycles of the tutorial prototype, each confirmed via grep for a version-unique marker.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The prototype was republished to the same URL five times in one session. A 200-based check would have declared success instantly every time — the URL already served the previous version. Polling for version-unique markers ('id="rtMap"' after the map fix, 'Where we are' after the readability pass) gave a truthful go-live signal each cycle for the cost of choosing one grep string. Reporting "live" to a user who then loads the stale version burns trust and a full test round on their device.

### Suggestion 8: Smoke-test every advertised view at every breakpoint — `AGENTS-MD-30f6eef273`

> **Smoke-test every advertised view at every breakpoint.** "Before handing a responsive UI to a user, enumerate its views and controls, then verify with an automated browser that each view is reachable at every CSS breakpoint and input mode the UI claims to support — including and especially the primary target device's width. Desktop eyeballing and a 21-check Playwright suite that navigated programmatically (window.openNode) both missed it; the user found it in minutes on the real device. The fix took ten minutes; the round-trip through the user cost a review cycle. One reachability matrix (views x breakpoints) driven by clicks, not JS calls, catches this class entirely.

### Suggestion 9: Deliver interactive HTML to users as a served URL, not a file attachment — `AGENTS-MD-1d2668719d`

### Suggestion 12: Daemonize ad-hoc dev servers; they die with the shell that started them — `AGENTS-MD-f777bfc27c`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-f777bfc27c-daemonize-ad-hoc-dev-servers-they-die-with-the-shell-that-st.md](./2026-07-05-1/AGENTS-MD-f777bfc27c-daemonize-ad-hoc-dev-servers-they-die-with-the-shell-that-st.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Daemonize ad-hoc dev servers; they die with the shell that started them.** "A background server started inside one Bash tool call (even with &) dies when that call's shell exits. Start ad-hoc servers with setsid, redirect their output, and verify with a curl to the actual endpoint at the top of any later step that depends on them — treat ERR_CONNECTION_REFUSED from a test as "my server is gone," not as an application bug."

Midway through prototype testing, a Playwright run failed with net::ERR_CONNECTION_REFUSED because the http.server launched in an earlier tool call had died with its parent shell. The failure looks exactly like a broken artifact and invites debugging the wrong layer. setsid plus a pre-flight curl made every subsequent run deterministic. Cost: one shell idiom; benefit: no false-negative test runs against a server that quietly stopped existing.
